# 2026-09-05 — Backups, where there were none

## What was missing

The audit turned this up and it outranked everything else found that day:

```
0 scheduled backup jobs
0 backup executions
/data/coolify/backups — empty
crontab — empty
```

Releases, tracks, producers, photos, contact messages and all 21 media objects
existed in exactly one place. The GitHub repository holds the code, not the data
or the uploads. A disk failure or a deleted VPS would have ended the project.

## What now runs

**03:00 — Postgres.** Coolify's own scheduled backup against the `supabase-db`
service database, 7 dumps kept. Not left to prove itself at 3am: dispatched once
by hand and verified. The result is a 252 KB `PGDMP` custom-format archive
containing 56 tables of data, `releases`, `tracks`, `producers`, `photos`,
`site_content` and `admin_users` among them — confirmed with `pg_restore --list`,
not by trusting the "success" status.

**03:30 — media.** `/root/backup-media.sh` archives the MinIO volume that holds
every uploaded image and audio file. The database dump does not cover these: the
rows reference the objects, the objects live in MinIO. 115 MB per archive, 7
kept, logged to `/data/coolify/backups/media/backup.log`. Verified by listing the
archive: 60 objects including `media/tracks`.

Ceiling is roughly 800 MB of archives against 96 GB, of which 24% is used.

## Restoring

Database:

```bash
docker cp <dump>.dmp supabase-db-u1u6nno8jxtc1tsqv1arokts:/tmp/r.dmp
docker exec -i supabase-db-u1u6nno8jxtc1tsqv1arokts \
  pg_restore -U postgres -d postgres --clean --if-exists /tmp/r.dmp
```

Media — stop the storage stack, replace the volume, start it:

```bash
cd /data/coolify/services/supabase
docker compose -p supabase stop supabase-minio supabase-storage
tar -xzf /data/coolify/backups/media/media-<stamp>.tar.gz -C volumes/..
docker compose -p supabase start supabase-minio supabase-storage
```

## The limit of this, stated plainly

**Both copies sit on the same disk as the data they protect.** This covers a bad
migration, an accidental delete, corruption — the failures that actually happen
most. It does **not** cover the scenario that motivated the work: the disk dying
or the VPS disappearing. For that the archives have to leave the machine.

Coolify supports that natively — a scheduled backup has `save_s3` and an
`s3_storage_id`, and no S3 storage is configured yet. Cloudflare R2 has a 10 GB
free tier, the account already exists, and 800 MB of archives fits inside it.

That is the right use of R2, and worth saying out loud given it was removed from
this project earlier today: the problem then was a *browser* holding write
credentials to a bucket. A server-side backup target holding its own token, never
compiled into a bundle, is the opposite arrangement.

It needs a new R2 API token, which only the account owner can create.
